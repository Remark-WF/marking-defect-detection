# Почему post-processing написан вручную

В проекте YOLO-модель экспортируется в ONNX/RKNN без полной логики post-processing. Нейросеть возвращает сырые предсказания, а Python-код вручную выполняет декодирование, фильтрацию и NMS.

Основной файл:

```text
src/pipeline/rknn_utils.py
```

Ключевые функции:

```text
letterbox_rgb()
decode_yolo_like_1xCxN()
nms_xyxy()
```

## Что считается post-processing

Для YOLO post-processing обычно включает:

1. Приведение выходного тензора к понятной форме.
2. Разбор координат box.
3. Применение sigmoid, если выходы не нормализованы.
4. Расчет confidence score.
5. Выбор класса.
6. Фильтрацию по confidence threshold.
7. Non-Maximum Suppression.
8. Перевод координат из letterbox-размера обратно в исходный кадр.

## Почему это не оставлено внутри экспортированной модели

### 1. RKNN лучше работает с нейросетевой частью

При конвертации YOLO в RKNN сложные операции post-processing могут не перенестись так же надежно, как обычные слои нейросети. Поэтому стабильнее конвертировать только backbone/head модели, а post-processing держать в Python.

### 2. Разные версии YOLO имеют разные выходы

В проекте использовались YOLOv5n, YOLOv8n и YOLO11n. У них могут отличаться:

- форма выходного тензора;
- наличие отдельного objectness;
- порядок координат;
- формат `xywh` или `xyxy`;
- количество каналов `C`.

Поэтому в `decode_yolo_like_1xCxN()` сделан универсальный декодер для нескольких вариантов:

```text
C = 5       -> [x, y, w, h, conf]
C = 4 + nc  -> [x, y, w, h, class_scores...]
C = 5 + nc  -> [x, y, w, h, objectness, class_scores...]
```

### 3. Нужен контроль над thresholds и NMS

Для производственного контроля важно быстро менять:

- confidence threshold;
- IoU threshold для NMS;
- пороги для отдельных классов;
- правила решения о браке.

Если post-processing зашит внутрь модели, такие настройки сложнее менять без повторной конвертации.

### 4. Проще искать ошибки между PT, ONNX и RKNN

Если результат RKNN отличается от PyTorch, ручной post-processing позволяет отдельно проверить:

- preprocessing;
- форму выхода модели;
- confidence;
- NMS;
- обратное преобразование координат;
- порядок классов.

Это сильно упрощает отладку на Orange Pi.

### 5. Бизнес-логика не должна быть частью модели

Решение `исправно / брак` зависит не только от нейросети, но и от правил контроля. Например, сколько `target_field` должно быть найдено, какие элементы обязательны, какой процент дефектных кадров считать браком по треку.

Такие правила лучше держать в коде пайплайна, а не внутри модели.

## Минусы ручного post-processing

- Нужно внимательно поддерживать соответствие preprocessing при обучении, экспорте и инференсе.
- При смене версии YOLO может потребоваться проверить форму выхода.
- Ошибка в декодере может ухудшить результаты даже при хорошей модели.

## Что проверять после переобучения или конвертации

1. Размер входа модели.
2. Порядок каналов BGR/RGB.
3. Нормализацию.
4. Letterbox padding.
5. Форму выходного тензора RKNN.
6. Количество классов.
7. Thresholds.
8. NMS.
9. Совпадение результатов PT и RKNN на нескольких одинаковых изображениях.

## Где это связано с кодом

- `src/pipeline/rknn_models.py` загружает RKNN-модель и получает сырые outputs.
- `src/pipeline/rknn_utils.py` декодирует outputs.
- `src/pipeline/run_pipeline_orangepi.py` применяет thresholds, проверяет ROI и принимает решение о браке.
