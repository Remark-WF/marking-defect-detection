# Обзор проекта

Проект решает задачу автоматизированного контроля качества маркировки продукции по видео с производственной линии.

Главная идея: не пытаться сразу классифицировать весь кадр, а разбить задачу на два этапа.

## Этап 1. Поиск этикетки

Первая модель YOLO получает полный кадр и ищет область этикетки. На выходе получается bounding box этикетки.

Зачем это нужно:

- уменьшается область анализа для второй модели;
- повышается стабильность проверки;
- уменьшается нагрузка на Orange Pi;
- можно сохранить crop этикетки для ручной проверки или доразметки.

## Этап 2. Проверка маркировки

Вторая модель получает только нижнюю/рабочую часть crop этикетки и ищет контрольные элементы:

- `anchor_icon`
- `anchor_lot`
- `anchor_volume`
- `target_field`

После этого применяется логика принятия решения. В текущей версии объект считается корректным, если найдены обязательные элементы маркировки в ожидаемом количестве. Если элементы отсутствуют или их количество отличается, объект считается дефектным.

## Версия для Orange Pi

Для Orange Pi 5 используются модели в формате RKNN FP16. Основной код находится в `src/pipeline`.

Ключевые файлы:

- `src/pipeline/run_pipeline_orangepi.py` - основной запуск пайплайна;
- `src/pipeline/rknn_models.py` - обертка над RKNNLite;
- `src/pipeline/rknn_utils.py` - preprocessing, decoding, NMS;
- `src/pipeline/utils_draw.py` - отрисовка результатов.

Дополнительно:

- `src/collector/collector.py` - сбор видео с камеры;
- `src/ui/operator_panel.py` - простая панель оператора.

## Что важно знать следующему разработчику

1. Большие файлы лежат не в Git, а во внешнем хранилище.
2. Для обучения нужны `.pt` модели и датасеты в YOLO-формате.
3. Для Orange Pi нужны `.rknn` веса, а не `.pt`.
4. Если меняется список классов, нужно менять не только датасет, но и логику `decide_defective`.
5. После переобучения обязательно проверить метрики и инференс на видео, а не только на validation split.
